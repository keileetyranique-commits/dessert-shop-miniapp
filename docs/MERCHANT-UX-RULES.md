# 商家易读化与“老板模式”设计规则

## 1. 目标用户

本产品首先服务普通餐饮小店、夫妻店、小型连锁和非技术商家。

设计假设：

- 商家不需要懂财务、统计、AI、数据库或软件工程；
- 一部分用户可能不熟悉专业术语；
- 商家通常在营业间隙操作系统，注意力有限；
- 手机、小屏幕、触屏和快速操作是常见场景；
- 系统应替商家做能自动完成的事情，而不是把内部参数转嫁给商家填写。

验收标准不是“功能存在”，而是：

> 第一次使用的普通店主，不看技术文档也大致知道下一步该做什么。

---

## 2. 默认使用“老板模式”

普通商家默认看到简单经营界面，不展示底层工程字段。

老板模式第一屏优先回答四个问题：

1. 今天/最近经营得怎么样？
2. 有什么需要注意？
3. 哪些商品或成本正在发生明显变化？
4. 系统建议我现在做哪 1～3 件事？

复杂功能进入二级页面或“高级设置”。

例如成本中心、BOM、成本快照、内部版本、bps、Pricing Engine 参数等，不应与日常“新增商品”“改价格”“看订单”平铺在同一层。

---

## 3. 先说人话，再给专业依据

默认文案必须让非专业商家理解。

禁止把下面这类内部表达直接作为主文案：

- “贡献利润率低于阈值”
- “SKU 成本 completeness=PARTIAL”
- “lossRateBps=2000”
- “Asia/Shanghai”
- “ACTIVE / INACTIVE”
- “计算版本 unit-cost-v1”

优先表达：

- “这个商品现在赚得比较少，再打折可能不划算。”
- “这个商品的成本资料还没填完整。”
- “损耗：20%。”
- “中国标准时间（北京时间）。”
- “营业中 / 已停用。”
- “本次成本按最新资料计算。”

必要的专业解释放在“查看详情 / 为什么 / 高级信息”中。

---

## 4. 结论优先，依据第二层

经营分析卡片默认结构：

1. **一句话结论**
2. **影响程度**
3. **建议动作**
4. “查看原因/趋势/详细数据”

示例：

> **五花肉最近越来越贵了**
>
> 继续上涨会影响 3 个菜品的利润。
>
> **建议：暂时不涨价，价格再上涨约 4% 时提醒我重新计算。**
>
> [查看价格趋势] [设置提醒]

不要先展示几十个指标，再让商家自己寻找结论。

---

## 5. 图表优先简单直观

默认优先使用：

- 趋势折线图：最近是涨还是跌；
- 简单柱状对比：这个月 vs 上个月；
- 排行：哪些商品最值得关注；
- 红/黄/绿风险卡：正常、注意、需处理；
- 进度/区间：距离警戒线还有多少；
- 经营计划卡：系统建议做什么。

禁止为了“数据感”堆复杂 BI 图。

颜色不能作为唯一信息来源；同时提供文字、图标或标签，保证色弱用户也能理解。

风险文案建议：

- 正常
- 值得关注
- 建议处理

避免制造恐慌的夸张措辞。

---

## 6. 表单：必填和选填必须分开

所有表单必须明确：

- **必填**
- **选填**
- **系统自动**

选填字段默认折叠或放入“更多设置”。

如果系统可以安全推导或设置合理默认值，就不要让商家填写。

### 门店创建

普通创建流程建议只要求：

**必填**
- 门店名称

**建议但可选**
- 地址
- 联系电话
- 营业时间

**系统自动**
- 时区：默认 `Asia/Shanghai`，界面显示“中国标准时间（北京时间）”
- 状态：默认营业中
- 内部 schema/version/tenant 字段

除非商家主动进入高级设置，否则不让用户输入 IANA 时区字符串。

### 商品创建

普通流程优先：

**必填**
- 商品名称
- 分类
- 售价

**推荐**
- 上传商品图片

**选填**
- 商品描述
- 库存设置
- 多规格
- 加料/选项

**系统自动**
- 默认上架状态
- 对只有一个规格的商品自动创建“默认规格”（如架构允许）
- 内部 ID、状态码、时间戳

多规格、复杂 Modifier、BOM 等使用“需要时再开启”的渐进式设置。

---

## 7. 中国商家本地化规则

### 金额

用户界面统一使用人民币“元”：

- 输入：`18.8` / `18.80`
- 显示：`¥18.80`
- 内部精确转换并存储：`1880 Fen`

普通商家页面禁止要求用户输入“1880 分”。

金额转换不得使用会造成误差的浮点计算方式。

### 百分比

用户输入/看到：

- `20%`
- `15.5%`

内部可使用 bps，但普通页面不显示“2000 bps”。

### 单位

内部值与用户文案分离，例如：

- each → 个
- g → 克
- kg → 千克/公斤
- ml → 毫升
- L → 升

### 状态

内部：
- ACTIVE
- INACTIVE

用户：
- 门店：营业中 / 已停用
- 商品：已上架 / 已下架
- 其他对象根据业务语境翻译，不直接显示枚举值。

### 时间

中国门店默认北京时间。时间输入优先使用日期/时间选择器，不要求商家手写 ISO 时间字符串。

---

## 8. 图片必须上传，不让普通商家填写 URL

商品、门店 Logo、营销图片等正常流程使用：

- 选择/拖拽上传；
- 上传进度；
- 图片预览；
- 更换；
- 删除；
- 文件类型和大小中文提示。

数据库可以继续保存 URL，但 URL 是系统内部结果，不是商家输入字段。

开发环境可使用本地/容器存储适配器；生产通过统一 Storage Adapter 接对象存储。不得把某家云存储写死进商品领域模型。

---

## 9. 日常导航接近成熟餐饮商家系统

优先采用普通商家熟悉的信息架构，例如：

- 首页
- 商品
- 订单
- 库存
- 营销
- 配送
- 经营分析
- 门店设置

成本、利润、BOM、Pricing、研判等复杂能力放在“经营分析”或相应二级页面。

基础 UI、表格、上传、筛选、商品编辑等优先复用成熟开源项目和成熟餐饮商家系统的交互范式；核心分析/利润/研判能力自研。

---

## 10. 超级研判输出规则

AI/规则系统不得给商家一篇长篇论文作为默认结果。

每次研判优先输出：

> **这次最值得做的 3 件事**

每个建议必须包含：

- 建议做什么；
- 为什么；
- 预计影响（明确标注“估算”）；
- 风险；
- 是否需要老板确认；
- 简单趋势图或对比图（如果有数据）。

示例：

> **建议把“梅菜扣肉”价格提高 ¥1**
>
> 五花肉采购价持续上涨，如果不调整，预计单份利润会继续下降。
>
> 预计影响：每月多保留约 ¥300～¥500 利润（估算）。
>
> [查看依据] [采纳] [暂不处理]

默认不展示“置信度 0.82”这种机器术语。可以改成：

- 依据较充分
- 依据一般
- 数据还不足

详情页再展示样本量、数据日期、模型一致性等专业信息。

---

## 11. 原料/市场/风险雷达的易读规则

不要写：

> “五花肉时间序列呈显著正向趋势，成本敏感度 0.42。”

写：

> **五花肉最近在慢慢涨价**
>
> 它占“梅菜扣肉”成本比较高，如果继续涨，这个商品会越来越不赚钱。
>
> [看趋势] [影响哪些商品] [生成应对方案]

趋势预测必须标明不确定性，不得把 AI 预测写成必然事实。

---

## 12. 经营计划必须可确认、可撤回

系统可以自动生成经营计划，但关键经营改变默认不能静默执行。

计划支持：

- 查看方案；
- 分项采纳；
- 修改；
- 暂不执行；
- 暂停；
- 使用最新数据重新研判；
- 比较新旧方案；
- 查看执行后的效果。

价格、活动、商品上下架等高影响操作必须经过权限和规则校验，必要时二次确认。

---

## 13. 不做暗黑模式

可以使用行为经济学、消费心理学和选择架构帮助商家提高转化，但不得：

- 假倒计时；
- 假库存；
- 假销量/假评价；
- 默认勾选收费加料；
- 隐藏费用；
- 制造虚假紧迫感；
- 通过难取消/难迁移故意锁定商家。

产品黏性来自持续价值，不来自人为制造退出障碍。

---

## 14. 开发验收清单

涉及商家可见界面的 PR，审查时至少检查：

- [ ] 是否首先用普通中文表达？
- [ ] 是否出现 Fen、bps、内部枚举、IANA 时区等工程字段？
- [ ] 金额是否以人民币元输入/显示并精确转换为 Fen？
- [ ] 百分比是否对商家显示正常百分数？
- [ ] 状态和单位是否已经中文化？
- [ ] 必填/选填/系统自动是否清晰？
- [ ] 能自动填写的字段是否仍在强迫商家填写？
- [ ] 高级配置是否可以折叠？
- [ ] 图片是否使用上传而不是 URL 输入？
- [ ] 是否有明确成功/失败中文反馈？
- [ ] 图表是否一眼能看出趋势或问题？
- [ ] 结论是否在数据明细之前？
- [ ] 商家是否能知道“下一步该做什么”？
- [ ] 危险操作是否有确认和历史保留？
- [ ] UI 是否参考/复用了成熟方案，而不是无理由重新造轮子？
- [ ] 手机/小屏和触屏操作是否可用？

不满足以上关键项，不应认为“功能完成”。
